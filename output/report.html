탐지 단계에서 발견한 실제 공급망 스캐너의 한계 (미탐 사례)

grype 기본 설정(match.java.using-cpes=false)으로 스캔하면 Tomcat 9.0.30 이미지에서 CVE-2020-1938(Ghostcat)이 전혀 탐지되지 않는다. grype가 Java fat/shaded jar의 오탐을 줄이기 위해 Java 패키지는 기본적으로 CPE 매칭을 쓰지 않기 때문이다 (벤더 CPE 룰 vs 실제 아티팩트 이름 불일치: tomcat-coyote.jar ≠ "apache:tomcat"). 이 PoC는 GRYPE_MATCH_JAVA_USING_CPES=true로 재스캔해 탐지했지만, 그 결과 전체 매치 수가 704개 → 791개로 늘어나 오탐 위험도 같이 커졌다 (라이선스 등 비보안성 패키지까지 과매칭 가능성). 실제 운영에서는 "CVE가 안 뜨면 안전하다"고 믿을 수 없고, 스캐너 설정 자체도 검증 대상이라는 뜻이다.

파이프라인

SBOM(syft, registry 직접 스캔) → 취약점 매칭(grype, java CPE 매칭 활성) → EPSS(FIRST API)·CISA KEV 보강 → server.xml/web.xml/context.xml 기반 도달성 판정(룰, CVE 3종) → 가중합 스코어링(통계) → 상위 3건만 LLM 조치안 생성(비용/환각 통제). 모든 수치는 실제 API/도구 호출 결과이며 임의 조작하지 않았다.
